# 국내 서지 API 연동 계획서

알라딘·네이버(및 대체) 무료 오픈 API 로 **국내책 서지정보와 책소개**를 확보한다.

---

## 1. 왜 필요한가

지금 국내책 서지 조회가 사실상 동작하지 않는다.

| 현재 소스 | 상태 |
| --- | --- |
| Google Books | 키 없는 익명 할당량이 소진되어 응답이 거의 비어 있음 |
| Open Library | 한국 아동서 데이터가 없음 |
| 웹 검색 그라운딩 | Gemini 무료 등급에서 막힘(429). Cloudflare → Gemini 자체가 지역 차단 |

그 결과 **Book Brief 가 모델의 기억으로 채워진다.** 그리고 방금 넣은 근거 검사
(`services/grounding.ts`)는 Brief 밖의 내용을 문항에서 걸러낸다. 두 사실이 겹치면 이렇게 된다.

```
빈약한 Brief → 모델이 기억으로 문항을 만듦 → 근거 검사가 걸러냄 → 문항 부족
```

실측 기준선 (2026-08-17, 『마당을 나온 암탉』, 배포 환경):

| 지표 | 값 |
| --- | --- |
| 확보한 출처 | **1건** (그마저 "AI 모델 지식" 기록) |
| Brief 길이 | 약 1,400자 (전부 모델 기억) |
| 1라운드 근거부족 탈락 | 1 / 10 |
| 목표 채우기까지 라운드 | 2 |

**국내 서지 API 는 "메타데이터를 예쁘게 하는 일" 이 아니다.** Brief 에 실제 출판사 책소개가
들어가면 모델이 인용할 근거가 늘고, 근거 검사를 통과하는 문항이 늘고, 라운드와 AI 비용이 줄어든다.

---

## 2. 확인한 사실

계획을 세우기 전에 **직접 호출해서** 확인했다. 인증 오류만 보고 "살아 있다" 고 판단하면 안 되므로,
**없는 엔드포인트를 같이 불러 대조군**으로 삼았다.

| API | 상태 | 판단 근거 |
| --- | --- | --- |
| **알라딘** `ItemSearch.aspx` · `ItemLookUp.aspx` | ✅ 살아 있음 | JSON 업무 오류 `{"errorCode":4,"errorMessage":"API출력이 금지된 회원입니다."}` 반환. 없는 엔드포인트(`Nonsense.aspx`)는 HTML 페이지를 주므로 구분됨 |
| **카카오** `dapi.kakao.com/v3/search/book` | ✅ 살아 있음 | 401 `cannot find Authorization : KakaoAK header`. 없는 경로는 404 `ResourceNotFound` 로 **다르게** 응답 |
| **네이버** `openapi.naver.com/v1/search/book.json` | ⚠️ **불확실 — 판정 보류** | 401 이 오지만 `nonsense.json` 도 **똑같은** 401 을 반환해 판별 불가. 3자 자료는 2026-07-31 종료(HUB 미이관)라 하지만, **공식 문서 페이지는 종료 안내 없이 그대로 게시되어 있다**(2026-08-17 확인) |

> 네이버 책 검색은 처음 401 응답만 보고 "살아 있다" 고 적을 뻔했다. 대조군을 넣어 보니 그 401 은
> 아무 것도 증명하지 않았다.
>
> 그 뒤 양쪽 증거가 갈렸다. 종료를 주장하는 3자 자료는 자기 모순이 있고(2027-06-30 유예 언급 후
> 부정), **공식 문서(`/docs/serviceapi/search/book/book.md`)는 개요·레퍼런스·오류코드·예제까지
> 온전히 살아 있고 종료 안내가 없다.** 문서가 남아 있는 것이 서비스가 산 증거는 아니지만,
> "종료됐다" 고 단정할 근거도 못 된다.
>
> **그래서 이 문서는 네이버를 "판정 보류" 로 둔다.** 결론은 §6 Phase 0-4 에서만 낼 수 있다 —
> 애플리케이션 등록 화면의 **사용 API 목록에 "검색" 이 있는지**, 그리고 실제 Client ID 로 책
> 검색이 결과를 주는지. 둘 다 로그인이 필요해 대신 확인할 수 없다.

### 알라딘 발급 조건 (조사 결과, Phase 0 에서 재확인)

- 알라딘 회원가입 → **TTB 사이트/블로그 등록** → 승인 (**1~2일 소요**)
  발급 페이지: <https://www.aladin.co.kr/ttb/wblog_manage.aspx> (회원 전용 — 로그인으로 넘어가는 것을 확인)
- 등록할 URL 로 배포 주소(`https://web-read-quiz.keymann.workers.dev`)를 쓸 수 있다
- 일일 호출: 일반 5,000회 / 프리미엄 100,000회 → **가족 규모에는 일반으로 충분**
- `ItemLookUp` 의 `OptResult` 로 부가 정보를 더 받을 수 있음 (어떤 값이 책소개·목차를 주는지는
  키를 받은 뒤 실측해서 채운다)

## 3. 무엇을 붙일 것인가

우선순위는 **확인된 것 먼저**다.

| 순위 | 소스 | 역할 | 왜 |
| --- | --- | --- | --- |
| 1 | **알라딘** | 주 소스 | 국내 도서 커버리지·출판사 책소개가 가장 좋다. 살아 있음이 확인됨 |
| 2 | **카카오 책 검색** | 보조 / 네이버 대체 | 살아 있음이 확인됨. `contents` 로 책소개를 준다. 키 발급이 즉시(승인 대기 없음) |
| 3 | 네이버 책 검색 | **조건부** | Phase 0 에서 아직 쓸 수 있다고 확인되면 추가. 아니면 건너뛴다 |
| — | Google Books · Open Library | 유지 | 원서·번역서에서는 여전히 유용하다. 지우지 않는다 |

> 네이버가 종료되었더라도 **요청 취지(국내책 검색 보강)는 카카오로 그대로 달성된다.** 둘 다
> 무료·한국어·`책소개` 필드를 가진 검색 API 이고, 구조가 거의 같아 어댑터 한 개 차이다.

### 후보로 검토했으나 이번 범위에서 뺀 것

- **국립중앙도서관 서지정보 API**, **도서관 정보나루** — 서지 정확도는 최고지만 책소개가 약하다.
  Brief 를 살찌우는 것이 목적이므로 2순위 이후로 미룬다.
- **교보문고** — 공개 무료 API 가 없다.

## 4. 설계

### 4.1 키를 어디에 두는가 — **부모별이 아니라 서비스 공용**

AI 키는 부모마다 따로 받는다(§25). **비용이 부모에게 청구되기 때문**이다.
서지 API 는 성격이 다르다.

| | AI 키 | 서지 API 키 |
| --- | --- | --- |
| 비용 | 부모 부담 | 무료 |
| 보관 | `parent_settings` (AES-GCM 암호화) | **Worker Secret** |
| 부모가 할 일 | 발급·등록 | **없음** |

알라딘은 승인에 1~2일이 걸린다. 부모마다 발급받게 하면 아무도 안 쓴다. 그리고 서지 조회가
부모의 AI 키 상태와 **무관하게 항상 동작**하는 것이 이 기능의 요점이다.

```
wrangler secret put ALADIN_TTB_KEY
wrangler secret put KAKAO_REST_KEY
```

키가 없으면 그 소스를 **조용히 건너뛴다.** 지금 Google Books 가 실패해도 파이프라인이 멈추지
않는 것과 같은 규칙이다(§`search/bibliographic.ts` 의 `getJson` → `null`).

### 4.2 구조 — 기존 모듈을 넓힌다

`src/search/bibliographic.ts` 는 이미 `BibRecord[]` 를 돌려주는 모양이다. 소스를 함수로 하나
더 붙이면 된다. **새 추상화를 만들지 않는다.**

```
src/search/bibliographic.ts
  fromAladin(hint)      → BibRecord | null     source: "aladin"
  fromKakaoBook(hint)   → BibRecord | null     source: "kakao-book"
  fromNaverBook(hint)   → BibRecord | null     source: "naver-book"   (조건부)
  fromGoogleBooks       (기존)
  fromOpenLibrary       (기존)

  lookup(hint) → BibRecord[]                   국내 소스를 앞에 둔다
```

`BibRecord` 는 그대로 쓴다. `description` 이 이미 있고 `collectSources` 가 그것을
`book_sources` 로 적재한다 — **화면·Brief·근거 검사 어디도 고칠 필요가 없다.**

### 4.3 매칭 규칙 — 이번에 가장 조심할 곳

표지 OCR 은 제목은 잘 읽지만 ISBN 은 자주 놓친다. 그러면 **제목으로 검색**하게 되는데,
동명이서·개정판·전집이 섞여 **다른 책이 매칭될 수 있다.**

근거 검사가 들어온 뒤로 이 위험이 커졌다. 잘못된 책의 책소개가 Brief 에 들어가면
그 책에 **"근거가 있는" 틀린 문항**이 만들어지고, 검사는 통과시킨다. 빈약한 Brief 보다 나쁘다.

그래서 이렇게 받아들인다.

```
ISBN 이 있으면            → ItemLookUp / 정확 조회. 그대로 신뢰
ISBN 이 없으면            → 검색 후 아래를 모두 만족할 때만 채택
                            · 제목 유사도가 충분히 높다
                            · 지은이 또는 출판사가 일치한다
                            어느 하나도 못 맞추면 버린다 (없는 것이 낫다)
```

유사도 계산은 이미 있는 것을 쓴다 — `services/question-checks.ts` 의 토큰 자카드, 또는
`services/grounding.ts` 의 어간 대조. **같은 일을 세 번째로 구현하지 않는다.**

### 4.4 책소개를 Brief 의 어디에 넣는가

알라딘·카카오의 `description`/`contents` 는 **출판사 마케팅 문구**다. 줄거리가 아니다.
그래서 `buildBrief` 의 `[소개]` 로 들어가고, `[줄거리]` 는 지금처럼 AI 조사 결과가 채운다.

여기에 §7 규칙이 걸린다 — **책 소개문만 읽어도 답할 수 있는 문제는 금지**다. 책소개가 Brief 에
들어오면 모델이 거기서만 문제를 만들려는 유혹이 생기고, 근거 검사는 그것을 "근거 있음" 으로
본다. 대응:

- 생성 프롬프트에 이미 있는 금지 항목을 유지하고, `[소개]` 는 **배경 지식**이며 출제 근거로는
  `[줄거리]`·`[주요 사건]`·`[등장인물]` 을 쓰라고 명시한다
- AI 검증(§10-4 "인터넷 검색만으로 답할 수 있는가")이 2차 방어선
- 실측으로 확인한다 — 책소개 도입 전후로 §7 위반 문항이 늘지 않는지 본다

### 4.5 출처 기록과 ToS

알라딘·카카오 모두 **출처 표시와 링크**를 요구한다. 이미 그 자리가 있다.

```
book_sources.source = "aladin" | "kakao-book"
book_sources.url    = 그 상품 페이지 URL   ← 반드시 채운다
```

참고 자료 카드가 `source` 를 사람이 읽는 이름으로 보여주므로(`SOURCE_LABEL`) 항목만 추가하면 된다.
`ui.el` 의 URL 스킴 검사와 `book.isStorableUrl` 이 이미 걸려 있어 안전하다.

주의: **책 본문을 저장하지 않는다.** 공개된 소개글·서평 요약만 쓴다(§6). 지금 규칙 그대로다.

### 4.6 호출 횟수

지금 `lookup()` 은 한 번의 조사에서 **2~3번** 불린다(`planResearch` + `applyResearch`, 서버
경로도 유사). 5,000회/일 한도에서 가족 규모라면 문제가 없지만, 같은 질의를 두 번 던지는 것은
낭비다. Phase 2 에서 조사 1회 = 조회 1회가 되도록 정리한다. **지금 당장의 차단 요인은 아니다.**

## 5. 측정 — 되었는지 어떻게 아는가

프롬프트를 고치는 일이 아니라 **입력 데이터를 늘리는 일**이므로, 효과는 숫자로 보인다.
아래 기준선은 오늘 실측한 값이다.

| 지표 | 지금 | 목표 |
| --- | --- | --- |
| 책 1권당 확보 출처 | 1건 (AI 지식 기록) | **2건 이상** (실제 서지·책소개) |
| `evidenceWeak` 경고 | 뜬다 | 안 뜬다 |
| 1라운드 근거부족 탈락 | 1 / 10 | **0 / 10** |
| 목표 채우기까지 라운드 | 2 | **1** |
| §7 위반(소개문만으로 답 가능) | 0 | **0 유지** ← 늘면 4.4 대응 |

같은 책(『마당을 나온 암탉』)으로 전후를 비교한다. 표지 이미지와 설정을 고정하면 변수는
서지 소스 하나뿐이다.

## 6. Phase 계획

### Phase 0 — 확인과 발급 (코드 없음)

> **1번 완료 (2026-08-17).** 배포된 Worker 에서 알라딘·카카오 모두 닿는다. Gemini 와 달리
> 지역 차단이 없다. 확인용 임시 진단 경로는 확인 직후 제거했다.
>
> | 대상 | 결과 | 대조군과 구별 |
> | --- | --- | --- |
> | 알라딘 `ItemSearch`·`ItemLookUp` | HTTP 200 · JSON `errorCode:4` · 약 0.5초 | ✅ 없는 경로는 HTML |
> | 카카오 책 검색 | HTTP 401 · 약 0.5초 | ✅ 없는 경로는 404 |
> | 네이버 책 검색 | HTTP 401 | ❌ 없는 경로도 같은 401 — **판별 불가, 4번에서 확인** |
>
> 응답 시간이 0.3~0.7초다. 조사 단계에 넣어도 체감 지연이 없다.

**가장 먼저 확인할 것은 기능이 아니라 "닿는가" 다.** Gemini 를 배포 환경에서 못 부른다는 사실을
전부 구현한 뒤에 알았다. 같은 실수를 반복하지 않는다.

| # | 할 일 | 판정 |
| --- | --- | --- |
| 1 | ~~**Cloudflare Worker 에서 `aladin.co.kr`·`dapi.kakao.com` 에 닿는지** 확인~~ ✅ | 닿는다 (위 참고) |
| 2 | 알라딘 TTB 등록·승인 (1~2일) | 키 확보 |
| 3 | 카카오 REST 키 발급 (즉시) | 키 확보 |
| 4 | ~~네이버 책 검색이 아직 신청 가능한지~~ ✅ | **쓸 수 없다.** 발급한 Client ID 로 `401 "Scopes are Empty"` — 키는 유효하나 검색 API 권한이 없다. **카카오로 대체 확정** |
| 5 | ~~실제 키로 조회 → 응답 필드 확보~~ ✅ | **관문 통과.** 알라딘 121~209자 + 카카오 250~253자. "두 줄" 은 아니다 (아래) |

1번은 배포된 Worker 에 임시 진단 경로를 두고 확인했고, 확인 직후 제거했다(PR #23 → #24).
없는 엔드포인트를 대조군으로 함께 불러 "응답이 왔다" 를 "닿았다" 로 착각하지 않게 했다.

> **5번 판정 (2026-08-17).** 관문은 통과했지만 기대보다 얇다.
>
> | 소스 | 책소개 분량 |
> | --- | --- |
> | 알라딘 `description` | 121~209자 (판본마다 다름) |
> | 카카오 `contents` | 250~253자 |
>
> "두 줄뿐" 은 아니므로 진행한다. 다만 **이 400자가 줄거리를 대체하지는 못한다** — 그리고
> §7 은 "소개문만 읽어도 답할 수 있는 문제" 를 금지한다. 그래서 이 연동의 실제 가치는
> 이렇게 정리된다.
>
> - **서지 정확도**: 표지 OCR 의 제목·저자·출판사·ISBN 오류를 바로잡는다 ← 가장 큰 가치
> - **잘못된 책 조사 방지**: 기준점이 생겨 엉뚱한 책을 조사하는 것을 막는다
> - **출처 확보**: `evidenceWeak` 경고 해소 (카카오까지 붙으면)
> - **줄거리는 여전히 AI 조사가 담당한다** — 이건 바뀌지 않는다
>
> 따라서 5장의 목표 중 "근거부족 탈락 0/10" 이 달성되더라도 그 공은 절반은 프롬프트 개선
> 몫이다. 책소개만으로 줄거리가 채워지리라 기대하면 안 된다.

### Phase 1 — 알라딘 어댑터 ✅ (2026-08-17)

**실측 결과** — 같은 책·같은 설정으로 전후 비교.

| 지표 | 전 | 후 |
| --- | --- | --- |
| 확보한 출처 | 1건 (AI 지식 기록) | **2건** (알라딘 + AI 지식) |
| 1라운드 근거부족 탈락 | 1 / 10 | **0 / 10** |
| 목표 채우기까지 라운드 | 2 | **1** |
| `evidenceWeak` 경고 | 뜬다 | 여전히 뜬다 ← 아래 |

**남은 것**: `evidenceWeak` 는 "웹 출처 2건 이상" 을 요구하는데, 알라딘 1건 + AI 지식 1건이라
기준을 못 채운다. 카카오가 붙으면(Phase 2) 웹 출처 2건이 되어 해소된다.

**돌려 보고 알게 된 것 — 계획의 오류 두 개**

1. **"ISBN 조회는 정확 조회라 그대로 신뢰" 가 틀렸다.**
   조회는 정확하지만 **그 ISBN 이 표지 OCR 에서 나온 값**이다. 실측: 『마당을 나온 암탉』
   표지에서 `9788958281252` 를 읽어 조회했더니 『즐거움과 상상력을 주는 과학』이 왔고,
   그것을 그대로 받아들여 참고 자료에 올렸다. 근거 검사는 그 책의 소개를 "근거 있음" 으로
   통과시키므로, **그 상태로 문항을 만들면 틀린 내용이 근거까지 갖춘다.**
   → ISBN 결과도 제목과 대조하고, 안 맞으면 ISBN 을 버리고 제목으로 되짚는다.

2. **같은 문제가 알라딘만의 것이 아니다.** 잘못 읽은 ISBN 으로 Google Books·Open Library 를
   불러도 다른 책이 온다. 그래서 검사를 소스별로 두지 않고 **결과가 모이는 `lookup()` 한
   곳**으로 옮겼다. 소스가 늘어날 때마다 같은 검사를 다시 붙이지 않는다.

**응답 처리에서 걸린 것**

- `description` 에 **태그 안에 ASP 블록**(`<% =qsUID %>`)이 중첩돼 온다. `<[^>]*>` 만 돌리면
  그 블록의 `>` 에서 끊겨 `">` 가 남는다 — 실제로 화면에 `">로 아이들만의…` 로 보였다.
  ASP 블록을 먼저 지운 뒤 태그를 지운다.
- `link` 가 `&amp;` 로 이스케이프돼 온다. 되돌리지 않으면 DB·화면에 그대로 남는다.
- `OptResult` 는 `Story`·`fulldescription`·`Toc` 모두 **아무것도 더 주지 않았다**(`packing` 만
  동작). 알라딘 책소개는 **121~209자가 전부**다.

### Phase 1 — 알라딘 어댑터 (원안)

- `fromAladin()` — ISBN 이면 `ItemLookUp`, 없으면 `ItemSearch`
- 매칭 규칙(4.3) 적용
- 키 없으면 건너뛰기, 실패해도 파이프라인 유지
- `SOURCE_LABEL` 에 "알라딘" 추가
- 테스트: `fetchMock` 으로 실제 응답 모양을 고정(성공·빈 결과·오류코드·다른 책 매칭 거부)

**완료 기준** — 알라딘 출처 1건이 `book_sources` 에 남고, Brief 의 `[소개]` 가 채워진다.

### Phase 2 — 카카오 어댑터와 병합 ✅ (2026-08-17)

**목표였던 `evidenceWeak` 경고가 사라졌다.**

| 지표 | Phase 1 후 | Phase 2 후 |
| --- | --- | --- |
| 확보한 출처 | 2건 (알라딘 + AI 지식) | **3건** (알라딘 + 카카오 + AI 지식) |
| `evidenceWeak` | 뜬다 | **안 뜬다** |
| Brief 길이 | 약 1,400자 | **1,607자** — `[출판사 소개]` 가 붙었다 |
| 1라운드 근거부족 탈락 | 0 / 10 | 1 / 10 (표본 1회. 아래 참고) |

`[출판사 소개]` 를 Brief 에 넣은 것이 이 단계의 본체다. 그 전까지 알라딘·카카오의 책소개는
`book_sources` 에만 쌓이고 **프롬프트에는 닿지 않았다** — `mergeMetadata` 가 AI 가 만든
description 을 우선하기 때문이다. 그래서 "Brief 를 살찌운다" 는 전제가 실제로는 성립하지
않고 있었다.

§7 대응도 함께 넣었다. `[소개]`·`[출판사 소개]` 는 **배경이며 출제 근거가 아니라고** 생성
프롬프트에 명시하고, 검증 프롬프트의 4번(검색만으로 답 가능)에 "소개만으로 답이 나오면 탈락"
을 더했다. 홍보 문구로 문제를 만들면 책을 읽지 않아도 풀린다.

> 근거부족 탈락이 0 → 1 로 늘어 보이는데 **표본이 각 1회라 판단할 수 없다.** 어휘가 늘면
> 통과가 쉬워지는 쪽이고, §7 지시가 세져 모델이 소개를 피하는 쪽이 겹친다. Phase 3 에서
> 여러 번 돌려 봐야 알 수 있다.

**돌려 보고 잡은 것 — 본문이 사라지고 있었다**

알라딘 `description` 은 꺾쇠로 감싼 책 제목을 **이스케이프 없이** 보낸다.

```
원본: <a href="…<% =qsUID %>"><나쁜 어린이표></a>로 아이들만의 생각을 …
```

`<[^>]*>` 로 태그를 지우면 `<나쁜 어린이표>` 까지 태그로 보고 지운다 — 실제로 그 제목이
통째로 없어져 `로 아이들만의…` 로 시작했다. **태그 이름이 ASCII 로 시작하는 것만** 지운다.

**조사 1회 = 조회 1회**

`books.bib_cache` 를 두어(0008) 준비 단계가 받은 서지를 적어 두고 반영 단계가 그것을 읽는다.
호출이 절반으로 줄지만 더 중요한 것은 **프롬프트가 본 서지와 병합에 쓰는 서지가 같아지는
것**이다. 두 번 부르면 그 사이에 응답이 바뀌어 모델은 A 를 보고 답했는데 서버가 B 로
제목·저자를 덮어쓸 수 있다.

**중복 제거는 하지 않았다**

계획에는 "같은 책을 여러 소스가 주면 ISBN 기준으로 합친다" 고 적었지만, 실제로 보니
**합치면 안 된다.** 알라딘과 카카오는 서로 다른 책소개와 링크를 가진 **별개의 인용**이고,
`evidenceWeak` 기준(웹 출처 2건)도 그래야 채워진다. 부모가 두 곳을 확인할 수 있어야 한다.
같은 URL 이 겹치는 경우는 `collectSources` 가 이미 걸러낸다.

### Phase 2 — 카카오(+조건부 네이버) 어댑터와 병합 (원안)

- `fromKakaoBook()` 추가. Phase 0-4 결과에 따라 `fromNaverBook()` 도
- `lookup()` 의 소스 순서·중복 제거 (같은 책을 여러 소스가 주면 ISBN 기준으로 합친다)
- 조사 1회 = 조회 1회로 정리 (4.6)

**완료 기준** — 국내책 한 권에서 출처 2건 이상, `evidenceWeak` 경고가 사라진다.

### Phase 3 — 실측과 조정

- 5장의 표를 실제로 채운다. 같은 책·같은 설정으로 전후 비교
- 책소개 도입으로 §7 위반이 늘었는지 확인 → 늘었으면 4.4 대응
- 근거 검사 임계값 재측정 — Brief 어휘가 늘면 점수 분포가 움직인다.
  `test/grounding.test.ts` 의 실측 표본을 갱신한다

**완료 기준** — 표의 목표치를 만족하거나, 만족하지 못한 이유가 문서에 남는다.
